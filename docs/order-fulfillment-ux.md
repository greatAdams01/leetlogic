# Order workspace and fulfillment milestones

Buyer and farmer order management now separates Order Details, Fulfillment, Payment and Activity History. The summary shows fulfillment method, status, progress and the role-specific next step. Mobile tabs sit outside the scrolling content and the main action stays in the page footer. Web tabs support arrow/Home/End keyboard navigation, selected-tab semantics and a matching tab panel; its primary action remains sticky. Existing unpaid checkout steps and staff logistics controls remain available separately.

Order details contain quantities, descriptions and packaging. Fulfillment contains pickup/destination context, permitted contact actions, courier/parcel tracking and the existing dispute process. Payment contains monetary breakdowns, payment verification, top-ups and recovery assistance. Activity contains persisted delivery events with readable titles and dates. Only the selected section is rendered for post-payment customer order management. Order lists use the same fulfillment labels; dispatched shipments leave the farmer packing queue. Pickup phone access remains gated on verified, allocated payment.

The API returns a role-scoped progress/capability projection based on the persisted order, buyer receipt timestamp, readiness/dispatch events, complete courier booking, disputes and settlement state. UI visibility does not authorize a transition: every write rechecks under the existing order row lock.

- Farmer readiness reuses `POST /orders/:id/delivery/ready`. Collection moves to PICKUP_READY; courier shipment status is preserved.
- Farmer dispatch uses `POST /orders/:id/delivery/dispatch`. It requires a funded, ready order and a complete booking (or an existing staff-verified manual shipment assignment). It creates one FARMER_DISPATCHED event and the existing buyer/farmer notification outbox entries. This is a farmer handoff attestation, not a forged courier tracking update. Unbooked or incomplete split shipments cannot be dispatched.
- Buyer receipt reuses `POST /orders/:id/delivery/confirm`. Pickup requires readiness; delivery requires the existing verified delivery/complete-parcel receipt rules. Farmer dispatch alone does not permit receipt or settlement. Duplicate confirmations return safely without changing the original timestamp, audit or notifications. Receipt adds one BUYER_RECEIPT_CONFIRMED event and notifies both parties.
- Financial holds, unresolved disputes, refunds and expired unsecured fulfillment prevent invalid actions. Buyers can use the existing dispute system rather than confirm receipt. Web now exposes that existing system beside fulfillment; mobile preserves its existing dispute component.

The customer-facing Completed milestone means buyer-confirmed fulfillment. The existing internal DELIVERED state and `deliveryConfirmedAt` continue to gate settlement; internal COMPLETED remains the later financial-settlement state. No money is released by a farmer dispatch or courier delivery event, and the UI does not invent a separate escrow bank account. Unconfirmed deliveries stay awaiting buyer confirmation; manual exceptions and disputes remain under the existing staff processes.

No new database migration or logistics/notification worker is required. Contracts, API and clients must deploy together. Validation covers role-specific actions, tab navigation, persistent mobile actions, privacy before payment, user confirmation prompts, duplicate writes, readiness/dispatch ordering, incomplete parcel bookings, financial holds, activity/outbox deduplication and independent funds retention. Provider delivery, real SMS/push, physical handoff and real-device visual layout were not exercised during implementation. No additional backend process was started.

Verification results: 79 payment integration tests and 77 delivery/address integration tests passed. The full mobile suite passed 404 tests; subsequent focused tests also cover the added packing-queue case. The full web suite passed 116 tests and the final checkout/fulfillment interaction run passed 40 tests including the added dispute path. Contracts passed 46 tests, and workspace type checks passed. These use mocked providers and isolated test databases; no real shipment, payment, payout, refund, or production configuration was changed.

## Farmer-first simplification

Farmer orders now use a separate, task-focused view on mobile and web. The default view contains the produce, large quantity, collection method, packing note/package count, available pickup date and one next action. The actions are **Order is ready** and **Rider has collected it**, with an explicit handoff question before dispatch is submitted. The three broad stages are Prepare, Hand over and Finished. Buyer collection, waiting, review and completed states explain what is happening without asking the farmer to operate payment or courier systems.

The farmer's four-tab navigation and dense tracking summary have been replaced by optional Pickup details, Money and Past updates sections. One section opens at a time, directly beneath its control. Addresses, parcel measurements, courier tracking, payment records, recovery/support actions and event history remain accessible. Get help uses the existing support/contact paths. Produce value is labelled as value, not available earnings or proof of escrow. The buyer order interface and all backend authorization, readiness, booking, dispatch, receipt and settlement rules are unchanged by this presentation refinement.

Copy uses plain language and the existing five-language dictionary. Native disclosure controls expose expanded state and have 56-pixel minimum targets; the main mobile action remains in the fixed footer. Web uses expanded-state controls and a large sticky action. Readiness and handoff continue through the existing endpoints and duplicate guards. Farmer-facing guidance is a shared projection of server capabilities, never a second authorization system. Real-device visual checks and usability sessions with farmers remain necessary; simplified wording is not a claim of usability validation.
