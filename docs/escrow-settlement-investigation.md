## Changes

- Automatic receipt release and staff release continue to use `requestRelease`, the same operation identity and the same worker/provider execution path. Blocked requests with no provider reference can now be resumed under the order lock; repeated approvals reuse the operation rather than creating another transfer.
- Admin order refunds resume blocked original refund operations. The worker checks financial holds, disputes, remaining held principal, existing releases, shipment state and destinations before submission. Bank refund payouts repeat the order checks before the final payout.
- Reconciliation now conditionally updates the exact status and provider reference read, with an expired or absent lease, and writes the audit record in the same transaction. A concurrent change returns a refresh instruction instead of being overwritten.
- A late worker error conditionally records its result only while it still owns the original processing lease. It cannot overwrite success confirmed concurrently by a webhook or a newer worker lease.
- Worker classification distinguishes preflight failures, rejected writes and reconciliation reads. A known provider reference always remains on the reconciliation path after a lookup error. Unknown submitted writes are never automatically resubmitted.
- Only insufficient balance, unavailable balance data and provider preflight outages are eligible for bounded automatic retries: the original operation must be blocked, without a reference or lease, due for retry, and have fewer than five execution attempts. Every execution repeats normal safeguards. Terminal provider rejections and unknown writes require review.
- Settlement attempts now create persistent finance alerts for blocked, failed or uncertain outcomes. Operations pending over 30 minutes are monitored. Successful verification resolves the operation alert. Existing attempt counts, leases, provider references, journals and audit records are preserved.
- Completed worker runs save a separate `payments-sandbox` or `payments-live` heartbeat. The admin panel warns after five minutes without a completed run. Production still requires the dedicated `worker:payments` service; API startup alone does not run that production worker.
- A recognized Bachs NGN charge/wallet rejection is recorded as `PROVIDER_WALLET_MISMATCH`, with actionable admin guidance. Arbitrary provider response text is not stored or exposed to customers.
- The order finance view now shows release attempts, their original recovery controls, escrow amounts, release eligibility and settlement state. Displayed eligibility remains advisory; the submission path checks it again.
- A verified direct refund or final bank refund payout creates one `PAYMENT_REFUNDED` event and recipient notifications within the financial transaction. An internal refund transfer is labeled as awaiting bank payout.
- Added a read-only sandbox diagnostic: `apps/api/scripts/diagnostics/settlement-readiness.ts`. From the repository root, run `node --env-file=.env --import ./apps/api/node_modules/tsx/dist/loader.mjs apps/api/scripts/diagnostics/settlement-readiness.ts`. It refuses live keys/mode, reads actual provider balances and original payment/operation states, and omits credentials and bank details.

No schema migration was needed. Historical transactions were retained. No payment flags or provider balances were changed. The only direct provider write performed during investigation was the explicitly sandbox-only replay described above, which Bachs rejected without creating a refund.

## Financial paths after the changes

1. Receipt confirmation and private photo are saved; the API requests release and the durable worker scanner recovers missed scheduling. Verified original payment, order fulfillment, financial holds and disputes remain release gates.
2. A release request creates or resumes one operation. The worker checks account readiness and available NGN, submits with the original idempotency key, and records the provider reference. Pending or uncertain results are reconciled. Only verified success writes the escrow release, commission, farmer earnings, inventory and notification records.
3. Admin recovery exposes that operation. Preflight blocks may be resumed. Unknown outcomes without a reference require provider discovery/linking; known references are read and reconciled. A provider-confirmed terminal failure permits a separately tracked reviewed retry.
4. Refund initiation checks that the order principal is still held and a release has not consumed it. The worker verifies the original charge and refundable route. Direct refunds stay pending until confirmed. Bank returns require both a transfer and a verified final payout; the intermediate transfer cannot complete the refund.
5. Payout to a farmer's external bank remains a separate withdrawal after escrow release credits their provider account/earnings. It requires payout enablement, an approved bank destination, fees, available balance and approval. Release to provider balance does not claim bank receipt.
